## Design Specificity Verdict

**LLM assessment:** The app reads as a generic CRUD form wearing the Weigh Station's colors without its materiality. Token values are copied correctly in several places (tabs, pending badge, entry-date), but the two screens seen every single session — login and the app-shell header — have no card, no elevation, no brand mark beyond a wordmark. The one genuinely authored touch ("Enregistré localement ✓" — correctly says "locally," not "saved") shows real intent; the rest of the surface doesn't carry it through.

**Deterministic scan:** Clean — `impeccable detect --json app/src` returned 0 findings, exit code 0. Legitimate clean result, not a skipped scan. Means no generic slop patterns — but a mechanical detector checks generic anti-patterns, not fidelity to a project's own custom DESIGN.md, which is exactly where Assessment A found the real gaps.

**Visual overlays:** No `[Human]` browser overlay — the Claude-in-Chrome extension isn't connected this session, so the live-server/injection flow was skipped for both assessments (declared fallback). Both agents independently scripted real logins via headless-Chrome CDP and captured login, entry-form, pending-badge, and entries-list screens as static evidence instead.

## Overall Impression

The bones are right — offline-first data model, honest microcopy, correct mobile input ergonomics — but the product's actual differentiator (audit-tracked corrections, never a silent overwrite) is invisible in the UI, and a validation bug quietly contradicts that same promise by coercing bad input to 0. Both assessments independently flagged the `navigator.onLine` staleness and the create/edit validation mismatch — that convergence is the strongest signal in this report.

## What's Working

1. **Honest offline microcopy** — "Enregistré localement ✓" specifically claims locally, not saved, correctly modeling the offline-first mental model instead of overclaiming.
2. **Token-literal fidelity where applied** — tabs, pending badge, and entry-date match DESIGN.md's Label typography and color specs precisely; the system was consulted, not approximated.
3. **Real mobile input ergonomics** — `inputMode="numeric"/"decimal"` on every number field plus 16px input font (avoiding iOS Safari's auto-zoom-on-focus) show attention to the actual "typing fast on a phone" use case.

## Priority Issues

**[P0] Silent fallback-to-zero on invalid numeric input**
- **Why it matters:** `Number(bagsMilled) || 0` (EntryForm.tsx) and the identical pattern in EntriesList's edit form directly contradict the product's own integrity principle. Both assessments hit this independently — B also flagged that the edit form's `value={draftEdit.bags_milled ?? 0}` snaps back to 0 mid-typing, and that the edit form lacks the `required`/`min`/`inputMode` attributes the create form has.
- **Fix:** Validate before submit; on failure, use the Oxide Red field-error state DESIGN.md already specifies instead of coercing to 0. Bring the edit form's input attributes in line with the create form.
- **Suggested command:** $impeccable harden

**[P1] The core differentiator is invisible in the UI**
- **Why it matters:** "Every correction is auditable, never silent" is the stated positioning vs. the old spreadsheet workflow — but the edit flow shows zero indication a correction is logged (no "was X →", no confirmation copy). Invisible at the exact moment it should build trust.
- **Fix:** Surface it inline — show the prior value beside the edit, add a one-line note that the change is recorded.
- **Suggested command:** $impeccable clarify

**[P1] Offline awareness is stale and tab-scoped**
- **Why it matters:** `navigator.onLine` is read once per render with no `online`/`offline` listener, and only exists on the "Mes entrées" tab — the entry form and header carry no connectivity indicator at all, in a product whose entire premise is connectivity awareness. Confirmed independently by both assessments.
- **Fix:** Lift the connectivity subscription to App.tsx once; surface a persistent indicator visible from both tabs.
- **Suggested command:** $impeccable harden

**[P2] Readout font misapplied — breaks the system's own Named Rule**
- **Why it matters:** The entries-list summary line applies the monospace Readout face to label words too ("Sacs:", "Revenu:"), not just the figures, and lays nothing out in a column — directly contradicting DESIGN.md's own Tabular Readout Rule.
- **Fix:** Split label (Body face) from value (Readout face, tabular-nums); lay the four figures out as a label/value grid.
- **Suggested command:** $impeccable typeset

**[P2] Login screen and header carry no Weigh Station identity**
- **Why it matters:** These are the two screens seen every session, and they're where the committed identity is weakest — no card, no elevation, no persistent brand mark.
- **Fix:** Wrap login in the Card spec already defined in DESIGN.md; give the header a compact wordmark/sync-status glyph.
- **Suggested command:** $impeccable polish

## Persona Red Flags

**Jordan (First-Timer):** "Email" (English) beside "Mot de passe" (French) on the very first screen reads like an unfinished translation. No hint text distinguishes "Autre" from "Notes." Confirmation is a 2-second fading line — Jordan has no persistent trace and must manually check "Mes entrées" to verify the entry landed.

**Riley (Stress-Tester):** Targets the `Number('') || 0` fallback directly by clearing a required field before submit. Toggles connectivity off, stacks drafts, and finds the pending badge shows only a bare count with no per-entry detail — `SyncResult.failed` is computed by sync.ts and then discarded in useSync.ts before it ever reaches the UI. Also finds the edit form's "Enregistrer" has no disabled/loading guard (unlike login), so it's rapid-double-tappable.

**Sam (Accessibility-Dependent):** Login's error message has no `role="alert"`/`aria-live` — a failed login is never announced. Focus indicator is a pure hue shift (border color only, no glow), a weak signal for low vision, doubly so in the direct-sunlight field conditions PRODUCT.md calls out. The save confirmation is silent to a screen reader — the single most important moment in the flow produces no announced feedback.

## Minor Observations

## Questions to Consider

1. If "every correction is auditable, never silent" is the actual differentiator over the old spreadsheet, and the UI never shows evidence of it, whose trust is that guarantee actually building?
2. When an operator reopens the app after hours offline to a bare "6 entrées non envoyées," what happens to trust in "never lose an entry" if that number doesn't visibly resolve — shouldn't the pending state be detailed enough to make the promise verifiable?
