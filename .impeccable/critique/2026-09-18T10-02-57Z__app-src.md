## Overall Impression

The five previously-identified issues are genuinely fixed — both assessments independently confirm the validation, status indicator, readout grid, login card, and audit-trail hints all work as specified. But testing the exact area this round touched (offline behavior) surfaced a more serious problem underneath: the "Mes entrées" screen only ever queries the server and never merges in the local IndexedDB drafts it has access to, so checking your own work while offline — the precise scenario the product exists to handle — produces a false "no entries" state instead of showing what's actually been captured.

## What's Working

1. **The readout grid is the clearest expression of "The Weigh Station" in the build** — monospace tabular-nums, right-aligned against left-aligned labels, confirmed live to visually snap into a column exactly like a mechanical counter.
2. **The offline/online header indicator is fast, honest, and correctly wired** — flipped color and text within one render frame of real online/offline events in both assessments' live testing, with no reload needed.
3. **Validation copy is short, in-language, and field-specific** rather than a single generic banner — respects the "entering four numbers quickly" use case.

## Priority Issues

**[P0] "Mes entrées" lies about data loss while offline**
- **Why it matters:** EntriesList.tsx only ever queries supabase.from('entries') and never merges in listDrafts() from IndexedDB. Verified live: go offline, open "Mes entrées" → ~6-7s frozen "Chargement…" → renders "Aucune entrée envoyée pour l'instant" despite 10 real entries on file. This is the exact scenario — unstable connectivity, operator checking their own work — the product exists to solve, and the UI's own second screen undermines "never lose an entry" at the worst possible moment.
- **Fix:** Merge listDrafts() into the rendered list (visually distinguished, e.g. a Pending Gold badge per entry, non-editable until synced); give loadEntries a fast offline branch that skips the network call entirely when !online; replace "Aucune entrée envoyée" with something true when offline.
- **Suggested command:** $impeccable harden

**[P1] No distinct "synced to server" confirmation state**
- **Why it matters:** "Enregistré localement ✓" shows regardless of whether the subsequent sync succeeds, fails, or is still pending. For a number that affects payroll, "saved locally" alone is ambiguous at the moment of highest stakes.
- **Fix:** Track sync outcome per submission and progress the confirmation from "Enregistré localement" → "Synchronisé ✓" once runSync confirms success.
- **Suggested command:** $impeccable clarify

**[P1] An already-open offline edit can fail silently and confusingly**
- **Why it matters:** "Corriger" is correctly disabled offline, but an edit already in progress has no such guard — "Enregistrer" stays live, and on failure shows raw error.message (English/technical) in an otherwise all-French interface.
- **Fix:** Disable "Enregistrer" when !online with inline copy; map known network failures to a French fallback message.
- **Suggested command:** $impeccable harden

**[P2] Optional vs. required fields are visually identical**
- **Why it matters:** "Autre" (optional) renders with the exact same weight as the three required fields — no asterisk, no "(optionnel)" tag.
- **Fix:** Add a small "(optionnel)" Label-style tag next to "Autre," or de-emphasize its label color slightly.
- **Suggested command:** $impeccable clarify

**[P3] Login screen has no offline-aware messaging**
- **Why it matters:** A failed login shows raw error.message with no branch for a network failure, and nothing acknowledges that authentication itself requires connectivity.
- **Fix:** Catch network-shaped errors and show a French, connectivity-specific message.
- **Suggested command:** $impeccable harden

The "Réessayer" retry link is plain underlined text with no button affordance — a small, low-contrast target for a one-handed tap.

**Sam (Accessibility-Dependent):** Error/success text pairs color with sufficient contrast (error red ~5.7:1, success green ~6.4:1) and adjacent text, so it's not color-only. But no field gets aria-invalid/aria-describedby wired to its error span, so a screen-reader user isn't told which field failed or moved to it on submit.

## Questions to Consider

1. If "never lose an entry to bad connectivity" is Product Principle #1, why does the one screen whose entire job is letting the operator verify that (EntriesList) never look at the local draft queue that principle depends on?
2. If "every correction is auditable, never silent" is a stated principle, why does the UI only ever show the single current prior value, with no way to see the full edit history the database is already recording? Is that the operator screen's job, or exclusively the future owner dashboard's?
